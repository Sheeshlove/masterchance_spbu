# MasterChance

[![Python](https://img.shields.io/badge/Python-3.11-blue.svg)](https://www.python.org/)
[![Aiogram](https://img.shields.io/badge/Aiogram-3.x-orange.svg)](https://docs.aiogram.dev/)
[![Docker](https://img.shields.io/badge/Docker-supported-blue.svg)](https://www.docker.com/)

Сервис для абитуриентов магистратуры: бот, сайт и десктоп-приложение. Он парсит конкурсные списки шести вузов — **СПбГУ, ВШЭ, ИТМО, МГИМО, МГУ, РАНХиГС** — считает симуляции методом Монте-Карло и выдаёт примерную вероятность зачисления с учётом приоритетов и возможных отказов других людей в очереди.

Данные вузов не смешиваются: у каждого свой конкурс, свои места и свой код абитуриента, поэтому на странице каждый вуз — на отдельной вкладке, а Монте-Карло считается по вузам по отдельности.

Честно говоря, идея не нова: многие руками смотрят на своё место в списке и прикидывают шансы. Бот просто делает это быстрее и более системно.

> 🚀 **Никогда этим не пользовались?** Пошаговая инструкция без единого
> технического слова — [КАК_ЗАПУСТИТЬ.md](КАК_ЗАПУСТИТЬ.md).
> Как поднять сервер, сайт и приложение в Telegram — [СЕРВЕР.md](СЕРВЕР.md).

## Что умеет бот

- Собирает данные о заявлениях обычными HTTP-запросами — без ручного обновления.
- Запускает симуляции Монте-Карло поверх актуальных данных и показывает вероятность поступления.
- Строит отчёты по проходным баллам и числу поданных заявлений на направление.

## Запуск

- Python 3.11+
- Токен Telegram-бота от [@BotFather](https://t.me/BotFather)
- Docker (если запускаете в контейнере)

### Через Docker

```bash
git clone <repository_url>
cd masterchance
```

Создайте `.env`:

```env
BOT_TOKEN=your_token_here

```

Запустите:

```bash

```

### Локально

```bash
pip install -r requirements.txt
python bot.py
```

Браузер не нужен: списки всех шести вузов читаются обычными HTTP-запросами.

### Веб-интерфейс «посмотри свои шансы»

Кроме бота есть сайт с тем же сценарием: вводишь **код абитуриента** — видишь
направления, шанс зачисления, проходные баллы и статус экзаменов. Это read-only
витрина поверх той же БД; вся логика расчётов — в общем
`GetApplicantForecastUseCase`, который используют и бот, и сайт (числа не расходятся).

```bash
pip install -r requirements.txt
python seed_synthetic.py        # синтетические данные для локального теста (опц.)
python web.py                   # → http://localhost:8080  (make run-web)
```

Хост/порт настраиваются через `WEB_HOST` / `WEB_PORT` (по умолчанию `0.0.0.0:8080`).
Маршруты: `/` — форма и результат, `/how` — как работает прогноз, `/healthz` — проверка живости.

### «Почему такой шанс?»

Одно число из Монте-Карло выглядит как гадание, поэтому рядом с каждым
направлением показывается расклад, из которого это число получилось: сколько
мест и заявок, каким по счёту абитуриент идёт среди тех, у кого баллы
выставлены, сколько человек идут с нулём, как балл соотносится с прогнозом
проходного, что даёт приоритет и сколько конкурентов сидят без согласия (именно
их модель разыгрывает на уход в другой вуз).

Тексты собирает `_build_reasons()` в том же `GetApplicantForecastUseCase` —
бот, сайт и десктоп только раскрашивают готовые `Reason(kind, text)`, чтобы три
интерфейса не начали объяснять одно и то же по-разному. Расклад берётся из
`ProgramRepository.get_competition_for_programs()` и считается по тем же полям,
что скармливаются модели: «соперник без согласия» здесь — ровно тот, кого MC
кладёт в пул оттока (нет согласия ни по одной заявке).

Развёрнутый ответ на вопрос «понижается ли проходной, если кто-то уходит»
(да, понижается — проходной равен баллу самого слабого из зачисленных) —
в `/how` и в команде бота `/how`.

### Баллы берутся из списков как есть

Окончательные списки выложены, поэтому модель ничего не додумывает: ноль в
списке — это ноль в конкурсе, и обогнать человека с выставленным баллом он не
может. Раньше `AdmissionMonteCarlo` дорисовывал недостающие баллы (KDE по
каждому экзамену, личное среднее абитуриента, глобальное распределение, плюс
«заморозка» нулей по истёкшим экзаменам) — это имело смысл, пока результаты ещё
не опубликовали. Теперь всё это убрано вместе с настройками
`MC_EXAM_FREEZE_ENABLED` / `MC_EXAM_GRACE_HOURS` / `MC_OPTOUT_MODE` и
зависимостью `scipy`.

Случайными в модели остались ровно два источника неопределённости, которых в
данных действительно нет: жребий на равных баллах и уход части абитуриентов без
согласия в другие вузы. Побочный эффект — пересчёт стал заметно легче: балл
считается один раз, а не заново в каждой из 10 000 симуляций.

#### В Docker

Образ один на бот и веб; что запускать — задаёт команда (`CMD` по умолчанию — бот):

```bash
make serve               # всё сразу: обновлятор + сайт + бот
make autoupdate          # только обновлятор (данные раз в 3 часа)
make autoupdate-logs     # смотреть, как идёт обновление
make autoupdate-stop     # остановить всё
```

`docker-compose.yml` поднимает три сервиса на одном образе и общей БД (`./data`):
`updater` считает данные, `web` и `bot` их показывают. Порт сайта намеренно
слушает только `127.0.0.1` — наружу пускает nginx, который держит сертификат
(см. [СЕРВЕР.md](СЕРВЕР.md)).

### Telegram Mini App

Сайт открывается и внутри Telegram — отдельной сборки нет. `static/telegram.js`
помечает документ классом `tg`, только если `Telegram.WebApp.platform` не
`unknown` (в обычном браузере объект тоже существует, и наивная проверка сняла
бы шапку на живом сайте). Дальше правила `.tg` в `styles.css` прячут логотип —
его показывает сам Telegram — и растягивают форму на всю ширину.

Вход в мини-апп появляется, только если задан `WEBAPP_URL` и он начинается с
`https://`: Telegram другого не принимает, а на `http` запрос упал бы при
старте бота. Без настройки бот работает как обычный бот.

## Десктоп-клиент (.exe)

Пользователь открывает `MasterChance.exe`, вводит свой уникальный код поступающего
и видит шансы — без браузера и без установки Python.

### Как это устроено (и почему именно так)

Монте-Карло **нельзя посчитать для одного человека**: модель разыгрывает конкурс
всей когорты (см. `RecalculateMonteCarloUseCase` — он читает `get_all_applications()` /
`get_all_applicants()`). Поэтому клиент не парсит все списки на машине пользователя
— это заняло бы минуты, раздуло `.exe` до сотен мегабайт и обрушило бы сотни
запросов на сервер вуза с каждого компьютера.

Вместо этого:

| Что | Откуда | Свежесть |
| --- | --- | --- |
| Шансы, проходные баллы | **снапшот** БД с посчитанным MC (скачивается и кэшируется) | по расписанию пересчёта на сервере |
| Ваши баллы, приоритеты, согласия | **живой парсинг** по фильтру `applicant_code` — один запрос | в момент нажатия кнопки |

Расчёты не дублируются: клиент, бот и сайт используют один и тот же
`GetApplicantForecastUseCase`, поэтому числа нигде не расходятся.

Если сети нет — клиент честно работает на сохранённом снапшоте и пишет об этом
в статусной строке.

### Запуск из исходников

```bash
pip install -r requirements-desktop.txt
python desktop.py          # или make run-desktop
```

Откуда качать снапшот, задаёт `SNAPSHOT_URL` (по умолчанию — GitHub Releases).
Кэш лежит в `%LOCALAPPDATA%\MasterChance` (Windows) или `~/.local/share/masterchance`.

### Публикация снапшота (серверная сторона)

После `update_lists.py` и `run_monte_carlo.py`:

```bash
make snapshot              # → dist/master-snapshot.db.gz
```

Полученный файл выкладывается туда, куда смотрит `SNAPSHOT_URL` (например,
в GitHub Releases с именем `master-snapshot.db.gz`). Клиент забирает его
условным GET, так что неизменившийся снапшот повторно не качается.

### Сборка приложения

PyInstaller собирает только под ту систему, на которой запущен, поэтому сборка
матричная — workflow `.github/workflows/build-desktop.yml` (вручную или по тегу
`v*`) прогоняет офлайн-тесты и собирает три варианта:

| Раннер | Артефакт | Для кого |
| --- | --- | --- |
| `windows-latest` | `MasterChance.exe` | Windows |
| `macos-14` | `MasterChance-macos-apple-silicon.zip` | Mac на M1/M2/M3/M4 |
| `macos-13` | `MasterChance-macos-intel.zip` | Mac на Intel |

На macOS собирается полноценный `.app`-бандл (иначе двойной клик в Finder
открыл бы Терминал), и пакуется через `ditto` — `upload-artifact` не сохраняет
флаг «исполняемый».

Локально:

```bash
pip install -r requirements-desktop.txt pyinstaller
pyinstaller packaging/masterchance.spec
# Windows → dist/MasterChance.exe   macOS → dist/MasterChance.app
```

Приложение **не подписано**: Windows покажет SmartScreen, macOS — «не удаётся
проверить разработчика». Как это обойти, расписано в
[КАК_ЗАПУСТИТЬ.md](КАК_ЗАПУСТИТЬ.md).

В сборку намеренно не входят `numpy/pandas/numba` — считает сервер,
клиенту нужен только SQLite и HTTP.

## Полный алгоритм запуска и использования

Поток данных: **программы в БД → списки заявлений → Монте-Карло → бот отдаёт вероятности**.

### 1. Окружение

Требуется Python 3.11+ и токен бота от [@BotFather](https://t.me/BotFather).

```bash
git clone <repo_url> && cd masterchance_spbu
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
```

### 2. Конфигурация `.env`

```env
BOT_TOKEN=<токен_от_BotFather>
ENV=dev
TIMEZONE=Europe/Moscow
DATABASE_URL=sqlite:///data/master.db
PARSER_PARALLELISM=4                 # сколько списков тянуть параллельно

# Какие вузы обновлять: all — все шесть. Или через запятую: spbgu,itmo
UNIVERSITIES=all
SPBGU_BASE_URL=https://enrollelists.spbu.ru/reports/PriemList02.php

# Стартовые страницы приёма остальных вузов. Пусто — берётся адрес по
# умолчанию из openlists/specs.py; разделы приёма вузы переносят каждый сезон.
HSE_LISTS_URL=
ITMO_LISTS_URL=
MGIMO_LISTS_URL=
MSU_LISTS_URL=
RANEPA_LISTS_URL=
```

Полный список параметров (отток и т.д.) — в `app/config/config.py`.

### 3. Инициализация БД

- **Свежая БД** — таблицы создаются автоматически при первом запуске любого скрипта
  (`Base.metadata.create_all`), уже с колонкой `university`.
- **Существующая БД** (была до мультивуза) — накатить миграцию; она добавит `university`
  и проставит её всем старым строкам:

  ```bash
  alembic upgrade head        # включает миграцию a1c2e3f4b5d6_add_university
  ```

### 4. Заполнение программ (сидинг) — до `update_lists`

`update_lists.py` берёт список программ **из БД** (`get_programs_by_university`), поэтому
программы/кафедры/институты должны быть засеяны заранее.

Каталог наполняется автоматически тем же проходом, что и списки: `update_lists.py`
обходит специальности текущей выгрузки отчёта и записывает институты,
направления и программы. Отдельный шаг сидинга не нужен.

### 5. Обновление данных (по вузам)

```bash
python update_lists.py           # каталог + списки + пересчёт Monte-Carlo

# только пересчёт MC (например, после обновления нескольких источников):
python update_lists.py --no-monte-carlo
python run_monte_carlo.py
```

`update_lists.py` парсит списки в N процессов, перезаписывает
заявки выбранного вуза, обновляет статистику и **сразу пересчитывает Монте-Карло**.

### 6. Запуск бота

```bash
python bot.py     # или make run (Docker)
```

Бот по коду абитуриента ищет его заявки и показывает вероятности из последнего пересчёта MC.

### 7. Регулярная эксплуатация (cron)

Одна команда: первый сбор сразу, дальше сам каждые 3 часа, переживает
закрытие терминала и перезагрузку сервера.

```bash
docker run -d --name masterchance-updater --restart unless-stopped \
    --env-file .env -v "$PWD/data:/app/data" -v "$PWD/dist:/app/dist" \
    masterchance:local scripts/autoupdate.py     # make autoupdate
```

Логи — `docker logs -f masterchance-updater`, интервал — `UPDATE_INTERVAL_HOURS`
(не чаще раза в 10 минут). Разовый проход без фона — `scripts/server_update.sh`.

Бот держится отдельным долгоживущим процессом; обновление дописывает БД, бот читает
свежие результаты.

### Источники данных

Все шесть источников закрыты общим контрактом `IUniversitySource`
(`discover()` — найти списки, `fetch()` — разобрать один), поэтому обновление,
параллельный обход и запись в базу для всех одинаковы
(`UpdateApplicationListsUseCase.execute_source`).

**СПбГУ** — отчёт «Списки подавших заявление»
(`enrollelists.spbu.ru/reports/PriemList02.php`), у него есть API:

- **каталог программ** — из встроенного в страницу JSON `reportMeta`
  (`discover_programs`); обновляется тем же проходом, что и списки;
- **списки абитуриентов** — `POST /api/reports/priem-list-02/data`, ответ
  приходит готовым HTML-фрагментом на специальность (`block_to_records`).

**Остальные пять** — общий движок открытых списков
(`app/infrastructure/parser/openlists/`). Он не знает вёрстки конкретного вуза:
со стартовой страницы приёма собираются ссылки на списки, а в самих списках
ищется таблица (или массив JSON) с колонками, которые обязаны там быть по
Порядку приёма — уникальный код поступающего, конкурсный балл, баллы за ВИ и
ИД, приоритет, согласие. Заголовки узнаются по синонимам (`openlists/columns.py`),
поэтому редизайн сайта вуза сам по себе ничего не ломает, а новый вуз — это
адрес в `specs.py`, а не новый парсер. Колонки с ФИО распознаются отдельно и
выбрасываются: сервис не должен уметь связать код с человеком.

Список приходит не только страницей. Движок читает и **файлы**: `.xlsx`
(стандартной библиотекой — это zip с XML, `openlists/sheets.py`), CSV и `.xls`,
внутри которого лежит обычный HTML — так выгружает половина вузовских систем.
Старый бинарный `.xls` требует `xlrd`, а PDF не читается вовсе; в обоих случаях
в логе будет прямая запись, а не молчаливый ноль.

**ВШЭ** — как раз такой случай: списки лежат файлами XLS по программам на
странице [`priem45.hse.ru/magstats.html`](https://priem45.hse.ru/magstats.html),
разбитой на разделы «кампус → форма обучения → основа». Берём только Москву и
Санкт-Петербург, только очную форму и только бюджет. Отбор идёт по разделу, в
котором стоит ссылка: обход запоминает заголовки над ней (`crawl.Link.context`),
иначе «Скачать в формате XLS» под Пермью неотличима от такой же ссылки под
Москвой.

Числа мест в списках ВШЭ нет вовсе — оно лежит в соседнем разделе «Статистика
поданных заявлений», отдельным файлом на кампус (`openlists/seats.py`). Оттуда
же берётся направление подготовки. Без этой сводки шанс считать не на чем:
конкурс — это отношение людей к местам.

Кампус входит в название программы («Дизайн (Москва)»), потому что входит в
конкурс: «Дизайн» в Москве — 30 мест, в Петербурге — 7, и это два разных
набора. Без кампуса они склеились бы в один код программы.

**Только очное и только бюджет** — общее правило для всех источников
(`_NEVER` в `specs.py` плюс отбор строк по колонке основы обучения). Заочники и
платники — другие конкурсы с другими местами: в одной таблице с бюджетниками
они завысили бы и число конкурентов, и проходной.

Адрес каждого источника переопределяется через `.env` (`HSE_LISTS_URL` и т.д.),
проверяется командой `python scripts/diagnose_source.py <вуз>` — она печатает,
сколько списков нашлось и какие колонки узнались.

**Идентификаторы программ** неймспейснуты ключом вуза (`app/domain/universities.py`):

| что | как | зачем |
| --- | --- | --- |
| программа | `hse:38.04.02:1f4a9c2b` | одно название в двух вузах — разные конкурсы |
| направление | `msu:01.04.02` | `department_code` — он же `exam_id` в Монте-Карло |
| абитуриент | `1645144` | **без префикса**: код единый для всех вузов |

Уникальный код поступающего выдаёт суперсервис, и во всех вузах он один и тот
же, поэтому в базе — одна строка на человека, а не на его заявку в каждый вуз.
Делится по вузам не абитуриент, а **конкурс**: вуз зашит в код программы, и по
нему же расходятся вкладки на сайте, прогоны Монте-Карло и «пролетел с магой».
Всё, что считается внутри конкурса, хранится с указанием вуза — вероятности по
коду программы, диагностика MC отдельной колонкой (`admission_diagnostics.university`).
Иначе прогон одного вуза затирал бы результат другого у того же человека.

Единый код даёт модели и то, чего у неё раньше не было: **согласие в другом
вузе**. Держать его можно только одно, поэтому конкурент, отдавший согласие
СПбГУ, из конкурса ВШЭ почти наверняка уйдёт — и это видно в списках, а не
угадывается по баллу. Такие уходят с вероятностью `MC_CONSENT_ELSEWHERE_LEAVE`
(по умолчанию 0.9 — не 1.0, потому что согласие отзывают и переподают), а для
тех, кто не подал согласие нигде, осталась прежняя сценарная оценка по
перцентилю балла.

Пользователю префикс направления не показывается (`display_code`), а введённый
код ищется как есть; варианты с префиксом (`find_applicant_keys`) остались
только ради снапшотов, собранных до этой правки.

## Тесты


скачивание снапшота проверяется на локальном HTTP-сервере), рабочая
`data/master.db` не трогается — корневой `conftest.py` уводит тесты на временную

## Структура проекта

Код разбит по слоям Clean Architecture:

```
app/
  domain/         # модели данных (dataclasses) + реестр вузов (universities.py)
  application/    # сценарии использования
  infrastructure/ # парсеры и работа с БД
    parser/
      spbgu/      # отчёт СПбГУ: у него своё API
      openlists/  # общий движок открытых списков (ВШЭ, ИТМО, МГИМО, МГУ, РАНХиГС)
      runner.py   # параллельный обход: один источник на процесс
  presentation/   # Telegram-бот (aiogram), веб-интерфейс (FastAPI), десктоп (tkinter)
    web/          # FastAPI-приложение: app.py, templates/, static/
    desktop/      # десктоп-клиент: ui.py, snapshot.py, live.py
migrations/       # миграции Alembic
packaging/        # спека PyInstaller для сборки .exe
tests/            # офлайн-тесты на фикстурах
```

## Разработка

### Makefile

```bash
make build        # собрать Docker-образ
make run          # собрать и запустить (бот)
make run-web      # запустить веб-интерфейс локально (uvicorn)
make run-bot      # запустить Telegram-бот локально
make run-desktop  # запустить десктоп-клиент из исходников
make seed         # залить синтетические данные для теста
make snapshot     # собрать снапшот БД для десктоп-клиента
make exe          # собрать MasterChance.exe (только Windows)
make test         # прогнать офлайн-тесты
make web-docker   # запустить веб в контейнере (порт 8080)
make compose-up   # бот + веб через docker compose
make compose-down # остановить docker compose
make push         # отправить образ в реестр
make bump-version # обновить версию (VERSION=x.y.z)
```

```bash
alembic upgrade head
```
